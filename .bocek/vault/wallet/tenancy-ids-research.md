# What ID type and tenant-root schema do production multi-tenant SaaS / game-backend systems ship, and what does Better Auth's organization plugin require for the `projects.organization_id` FK target?

## Question

Q1 + Q2 of the wallet gap-cluster /research queue, executed in parallel because they interlock:

- **Q1 (G1 in `.bocek/vault/wallet/gaps.md`):** `players.id` UUID-vs-BIGINT vault drift between `[[player-auth]]` (UUID, newer 2026-05-03) and `[[wallet-mechanics]]` (BIGINT, older 2026-05-02). Q3's pgledger source-walk surfaced **prefixed ULID** as a real third option. What ID type do production multi-tenant SaaS / game-backend tenant-member tables ship, and which option (UUID v4 / UUID v7 / BIGSERIAL / prefixed-ULID / Better Auth 32-char alphanumeric) wins for BokChoy's storage + opacity + monotonic-locality + RLS-compatibility trade-offs?
- **Q2 (G2):** `projects` tenancy-root table schema undefined. The FK target for `players.project_id`, `transactions.project_id`, every multi-tenant RLS policy via `current_setting('app.current_tenant')::UUID = project_id`. Hard dependency on Better Auth's `organization.id` type (`projects.organization_id` FK, per `[[backend-stack]]`).

- **Production reference:** ✓ — Better Auth source `b03a45a` (tier 1, configurable ID generation verified by source-walk); pgledger `b3143a3` (tier 1, prefixed ULID over UUIDv7, already source-walked in `[[wallet-functions-research]]`); Supabase Auth `auth.users.id UUID` (tier 2 docs verified via search); Stripe Customer ID format (tier 2 docs).

## Sources examined

### S1 — Better Auth source

- **Tier:** 1 (production code, public repo, pinned commit, named maintainers)
- **Provenance:** `github.com/better-auth/better-auth`, commit `6b03a45a14d905aa070068290adfedfd4c5f4e2d` (2026-05-03). Read linearly: `packages/better-auth/src/plugins/organization/schema.ts`, `packages/better-auth/src/db/get-migration.ts:285-372`, `packages/better-auth/src/context/create-context.ts:222-237`. - **Author context:** Better Auth project, active development; published OSS auth library used by production teams. Project commits up-to-current-week.
- **What it tells us:**
  - **Default ID generator:** `generateId(size?: number) => createRandomStringGenerator("a-z", "A-Z", "0-9")(size || 32)` per `@better-auth/core/utils/id`. Produces a 32-character alphanumeric string from 62-char alphabet. Entropy: 32 × log₂(62) ≈ 190 bits.
  - **Configurable via `advanced.database.generateId`:**
    - `"uuid"` → migration emits `uuid` column type for Postgres (`get-migration.ts:346`); runtime generator switches to `crypto.randomUUID()` (`create-context.ts:230-231`) — **UUIDv4 specifically**, not v7.

    - `(args) => string` (custom function) → runtime calls it (`create-context.ts:227-228`); migration still keys off `"uuid"` vs `"serial"` strings, so custom function may need to coordinate with manual schema choice.
  - **`organization.id` shape:** `id: z.string().default(generateId)` per `schema.ts:293`. Always Zod string; underlying Postgres column type follows `advanced.database.generateId`.
  - **Other org-plugin tables:** `member`, `invitation`, `team`, `teamMember`, `organizationRole` — all use `generateId` for their own primary keys, all FK to `organization.id` and `user.id`.

### S3 — Stripe Customer ID format

TEXT-typed throughout. Variable-length, not fixed-format like UUID. Visually self-documenting in logs and dashboards.

### S4 — pgledger source (prefixed ULID, cross-referenced from Q3)

- **Tier:** 1 (production code, already source-walked in `[[wallet-functions-research]]`)
- **Provenance:** `github.com/pgr0ss/pgledger@b3143a3`, `pgledger.sql:1-40`. Observed 2026-05-04.
- **What it tells us:** prefixed ULID format `pgla_01HXXX...` for accounts, `pglt_` for transfers, `pgle_` for entries. ULID generated from UUIDv7 then converted to ULID (Crockford-base32) via vendored `scoville/pgsql-ulid`. On Postgres 18, native `uuidv7()`; on Postgres ≤17, fallback `pgledger_uuidv7_microsecond()` SQL implementation. TEXT primary key column type. Type-distinct in logs (prefix tells what kind of ID it is). Monotonically increasing (UUIDv7 timestamp prefix → B-tree locality similar to BIGSERIAL).

### S5 — UUIDv7 vs UUIDv4 vs BIGSERIAL benchmark

- **Tier:** 4 (engineering blog, named author, no Postgres-committer credential disclosed)
- **Provenance:** `mblum.me/posts/pg-uuidv7-benchmark/`, observed 2026-05-04 via WebFetch. Author: Michael Blum, independent engineering blog.
- **Author context:** Independent technical blog. No published Postgres-committer or large-scale-system credentials surveyed. Test scale is small (44,142 rows, Postgres 15, hardware unspecified) — extrapolates to a *trend* claim, not a *production-validated* claim.
- **What it tells us:** measured insert performance on Postgres 15:
  - **UUIDv4 BTREE primary key**: avg 35,606 ns, p90 792 ns
  - **UUIDv7 BTREE primary key**: avg 18,195 ns, p90 375 ns
  - UUIDv7 BTREE inserts ~49% faster than UUIDv4 BTREE
  - UUIDv7 index ~25% smaller than UUIDv4 index for same row count
  - BIGSERIAL not measured in this benchmark; established theoretical upper bound (sequential inserts → minimal page splits, smallest index)

  Underlying mechanism: UUIDv4's randomness causes B-tree page splits and fragmentation as new keys land at random index positions. UUIDv7's monotonic timestamp prefix causes new keys to consistently land at the right edge of the B-tree, near-zero page splits, sequential write amplification. Same mechanism that makes BIGSERIAL fast.

### S6 — RFC 9562 (UUIDv7 spec) + Postgres 18 native function

- **Tier:** 2 (official IETF spec + Postgres official release notes)
- **Provenance:** RFC 9562 (`datatracker.ietf.org/doc/rfc9562/`, published 2024-05); Postgres 18 release notes mentioning native `uuidv7()` (per Nile blog Source 7, also referenced in pgledger.sql:1-2 comment). Observed 2026-05-04.
- **Author context:** IETF UUID working group + Postgres Global Development Group.
- **What it tells us:** UUIDv7 layout is 48-bit Unix epoch milliseconds + 12 random bits + 6 version bits + 2 variant bits + 62 random bits. Effective randomness: 74 bits in the suffix (or 122 bits total when including the 48-bit timestamp, which is functionally non-random for opacity but distinguishes globally over time). Birthday collision at 74 effective-random bits ≈ N²/2⁷⁴: at 1B IDs ≈ 5×10⁻⁴ within the same millisecond — negligible across the whole product lifetime.

  Postgres 18 ships `uuidv7()` as a built-in function. Postgres 17 (BokChoy's current per `[[local-docker]]` `supabase/postgres:17.6.1.113`) requires either a SQL-defined function (pgledger's `pgledger_uuidv7_microsecond()` is one such, MIT-licensed, ~10 lines) or an extension.

### S7 — BIGSERIAL enumeration-attack class

- **Tier:** 3 (multiple independent post-mortems, advisories, and OWASP guidance)
- **Provenance:**
  - HN discussion `news.ycombinator.com/item?id=20005674` ("Yet another security vulnerability caused by sequentially incremented IDs"), 2019.
  - OWASP Web Security Testing Guide §4.3.4 "Testing for Account Enumeration and Guessable User Account."
  - Security Boulevard 2023-03 "Opaque IDs: the ultimate protection against enumeration attacks."
  - TrustedSec 2024 advisory "Watch Out for UUIDs in Request Parameters" (counter-position: UUIDs themselves can be misused — UUIDv1 leaks MAC + timestamp; UUIDv4 is the safe default).
  - Sprocket Security writeup on tenant enumeration attacks. All observed 2026-05-04 via web search.
- **What it tells us:**
  - BIGSERIAL leaks: signup order, total customer count, customer creation rate, time-to-customer for any specific signup. An attacker probing `/api/customers/1`, `/customers/2`, ... `/customers/N` learns the customer count + ordering even if the auth on each endpoint is correct. In multi-tenant SaaS this is direct competitive intelligence (how many customers does the SaaS have? at what rate are they signing up? who signed up before/after a known customer?).
  - UUIDv4 + UUIDv7 both defeat enumeration. UUIDv1 (MAC-based, timestamp-leaking) is rejected; UUIDv4 (fully random) and UUIDv7 (timestamp-prefixed but with random suffix) both have ≥74 bits of guess-resistance.
  - **TrustedSec contradiction:** UUIDs can leak via UUIDv1 (MAC + timestamp) or via predictable random sources (Math.random, weak RNG seeds). For BokChoy: `crypto.randomUUID()` (Node.js / browser stdlib) uses cryptographically-secure RNG per WHATWG Web Crypto spec; pgledger's `gen_random_uuid()` uses Postgres pgcrypto random. Neither leak. UUIDv1 is rejected on the BokChoy side regardless.

- **Tier:** 4 (engineering blog roundup, multiple sources, no single canonical reference)
- **Provenance:** Web search 2026-05-04 — `dev.to/pipipi-dev/building-multi-tenant-saas-as-a-solo-developer`, `flightcontrol.dev/blog/ultimate-guide-to-multi-tenant-saas-data-modeling`, `workos.com/blog/developers-guide-saas-multi-tenant-architecture`, plus Vercel Multi-Tenant Template + B2B Starter Kit (commercial templates).

- **What it tells us:** the dominant column set for tenant-root tables across surveyed multi-tenant SaaS:
  - `id` (UUID dominant in modern Postgres-stack systems; TEXT alphanumeric in Stripe-style)
  - `name` (display name)
  - `slug` UNIQUE (URL-safe, often subdomain — e.g. `acme` → `acme.app.example.com`)
  - `owner_id` / `created_by` (FK to user/account)

  Optional but common: `billing_customer_id` (Stripe customer FK), `domain` (custom domain support), `region` (multi-region deploys), `deleted_at` (soft-delete posture).

## Findings

### F1 — Better Auth's `organization.id` type is configurable; `"uuid"` aligns with Postgres-canonical convention

Better Auth does NOT force a specific ID type. The `advanced.database.generateId: "uuid"` option produces UUIDv4 column type + `crypto.randomUUID()` runtime generation. The default (no config) produces a 32-char alphanumeric TEXT — non-UUID, BokChoy-incompatible with the `current_setting('app.current_tenant')::UUID` GUC pattern in `[[multi-tenant-rls-research]]`. **BokChoy must explicitly set `advanced.database.generateId: "uuid"` in the Better Auth config; otherwise organization IDs are TEXT and the entire RLS chain breaks at the first cast.**

The custom-function hook (`generateId: ({model, size}) => string`) lets BokChoy plug in a UUIDv7 generator if v7 is preferred. The custom function still requires migration-side coordination — Better Auth's migration generator only emits `uuid` Postgres type when the literal string `"uuid"` is set; a custom function would need either manual migration overrides or accept that the column stays TEXT and the function returns a UUIDv7-string.

### F2 — UUID dominates in Postgres-native multi-tenant SaaS; prefixed-text dominates in API-public SaaS

Two production patterns exist:

- **UUID-everywhere (Postgres-native):** Supabase Auth, all surveyed Postgres SaaS multi-tenant guides, Vercel Multi-Tenant Template. Wins because: native Postgres `uuid` type (16 bytes binary), `gen_random_uuid()` built-in, RLS GUC casting (`current_setting()::UUID`) works directly, partition pruning unaffected, all standard tooling integrates. Loses because: opacity-only — UUIDs are not human-readable in logs or dashboards; ID context (is this a player? a wallet? a transaction?) requires column-name discipline.
- **Prefixed-text (API-public):** Stripe, pgledger. Wins because: self-documenting (`cus_xxx` is unambiguously a customer), URL-safe, support engineers can read IDs in tickets and dashboards. Loses because: TEXT column is 2× storage of UUID binary, requires custom generation function (UUIDv7 → ULID conversion + prefix concat), every join/comparison runs on TEXT, RLS GUC casting breaks (the natural shape `current_setting('app.current_tenant')::TEXT` works but loses the type-safety UUID gives).

Both are production-cited tier 1+2. The choice is stack-conditional, not universal.

### F3 — UUIDv7 dominates UUIDv4 on B-tree insert locality and index size; both defeat enumeration equally

UUIDv7's monotonic timestamp prefix provides B-tree insert locality similar to BIGSERIAL — new keys land at the right edge of the index, page splits are near-zero, write amplification is minimal. UUIDv4's randomness causes pessimal B-tree fragmentation. Per S5 benchmark: UUIDv7 inserts ~49% faster, index ~25% smaller. The benchmark scale is small (44k rows) but the mechanism is theoretical (B-tree behavior under random vs sequential inserts is well-established) — at 240M-row scale (BokChoy `transactions` projection per `[[wallet-mechanics]]` Failure mode 7), the gap should grow, not shrink.

UUIDv7 has 74 effective-random bits in the suffix. Birthday collision at 1B IDs within the same millisecond ≈ 5×10⁻⁴; across the product lifetime collision is functionally zero. UUIDv4 has 122 effective-random bits; collision profile is even better but irrelevant at any plausible scale (both are negligible).

Both defeat enumeration attacks per S7.

**Postgres 17 (BokChoy's current) does not ship native `uuidv7()`.** Postgres 18 does. Two options for BokChoy on Postgres 17:
- Adopt UUIDv4 today (`crypto.randomUUID()` + Postgres `gen_random_uuid()`); upgrade to UUIDv7 when Supabase ships Postgres 18.
- Transcribe pgledger's `pgledger_uuidv7_microsecond()` SQL function (10 lines, MIT-licensed) into BokChoy's bootstrap migration; use `bokchoy_uuidv7()` as the default for `id` columns. Forward-compatible — drop the function when native arrives.

### F4 — BIGSERIAL is rejected for customer-facing IDs in BokChoy's threat model

S7's enumeration-attack class is real and load-bearing for BokChoy: every customer-developer's `project_id` is exposed via API responses (the SDK embeds it in every request); their `player_id` rows leak via support tickets, error reports, customer-support tooling. BIGSERIAL leaks signup order + total project count + project-creation rate to anyone who can probe a single endpoint. At BokChoy's positioning (PLG funnel via `[[wedge-decision]]`), competitive intelligence on customer count + signup velocity is real-money valuable — that data point alone is what investors and competitors pay for.

The storage savings BIGSERIAL gives (~8 bytes vs UUID's 16 bytes per FK column) are bounded — at the `transactions` projection scale (240M rows × 8 bytes saved on `player_id` column ≈ 2 GB) the cost is ~$5–10/month at managed Postgres pricing. The competitive-intelligence leak is unbounded in cost. Storage is a wrong axis to pick on here.

### F5 — Prefixed-text rejected for BokChoy's stack despite the UX benefit

The Stripe / pgledger prefixed-text pattern wins on log readability and customer-support UX. For BokChoy specifically, the cost-benefit fails because:

- **`current_setting('app.current_tenant')::UUID = project_id` shape across every RLS policy** is the canonical pattern in `[[multi-tenant-rls-research]]` Sources 9, 10, 14. Every protected table's RLS policy references this UUID-cast. Prefixed-text would require rewriting every policy to cast TEXT — workable, but breaks the pattern and the existing `[[wallet-mechanics]]` §8 spec.
- **Postgres partition pruning** confirmed working with scalar `current_setting()::int` against partition-key columns per `[[multi-tenant-rls-research]]` Source 17 (Marcelo Zabani pgsql-hackers 2024-08-07). Same shape works for `::UUID`. Prefixed-text would not break pruning (it's still scalar on partition key) but would lose the type-safety the cast provides.
- **Storage 2×** — TEXT prefix+ULID at 31 bytes vs UUID 16 bytes binary. At 240M-row `transactions` × 16 bytes/row × 4 ID columns (id, project_id, wallet_id [BIGINT, separate], player_id) ≈ ~15 GB ledger-wide ID-column overhead vs UUID. Bounded but real.
- **Tooling friction** — every Drizzle ORM definition, every sql template literal, every RLS policy, every test fixture must handle TEXT IDs. Idiomatic Postgres-on-Drizzle is `uuid('id').primaryKey().defaultRandom()`; prefixed-text is `text('id').primaryKey().$defaultFn(() => generatePrefixedUlid('pl'))`. The latter is workable but every developer onboarding pays the friction.

The opacity benefit (Stripe-style readable IDs in support tickets) is real. The trade-off favors UUID for BokChoy's stack-shape. Vault as rejected alternative with named winning condition: **revisit if customer-facing IDs become a documented support-engineering bottleneck (e.g., support tickets routinely cite "tx 7a3f..." and engineers waste time figuring out what kind of ID that is) AND the migration cost is acceptable.**

### F6 — `projects` schema baseline derived from S8 + project-specific vault constraints

The minimum viable `projects` schema for BokChoy MVP, derived from S8 dominant pattern + named constraints from existing vault entries:

```sql
CREATE TABLE projects (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id      UUID NOT NULL REFERENCES "organization"(id) ON DELETE RESTRICT,  -- Better Auth org plugin table; quoted because Better Auth uses lowercase singular
  name                 TEXT NOT NULL,
  slug                 TEXT NOT NULL,
  is_child_directed    BOOLEAN NOT NULL DEFAULT FALSE,  -- per [[player-auth]] §4
  status               TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'paused', 'archived')),
  settings             JSONB NOT NULL DEFAULT '{}'::jsonb,  -- per-project config + plan limits
  created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (organization_id, slug)  -- slug unique within owning organization
);

CREATE INDEX idx_projects_organization ON projects (organization_id);
```

**Open in this baseline (deferred to /design or to the Q4–Q7 follow-ups):**
- **Environment model.** `[[idempotency-strategy]]` says dev/staging/prod are *separate projects*. No `environment` column needed. Vaulted; design confirms.
- **API key surface.** Per-project keys for SDK auth per `[[player-auth]]` §1 (owned auth, separate api_keys table FK'd to projects). Schema for `api_keys` table is a separate decision; not blocking the wallet primitive.
- **Soft-delete.** Above schema uses `status = 'archived'` rather than `deleted_at`. Single status column is simpler at MVP; soft-delete with `deleted_at TIMESTAMPTZ` can be added later if audit-retention demands it. /design can pick.
- **Region.** Single-region MVP per `[[mvp-feature-sequence]]`. No `region` column at MVP.
- **Billing.** Stripe customer FK lives on `organization` (Better Auth org plugin's billing surface), not on `projects` — projects inherit billing context from their org per the customer-as-org pattern in `[[backend-stack]]`. No `billing_customer_id` on projects.

The baseline above is implementable today; the deferrals are scope-control, not gaps.

### F7 — `players.id` resolution: UUID wins for BokChoy

Per the Q1 evidence stack:
- **Production-cited:** Supabase Auth UUID (S2). `[[player-auth]]` §2 already committed UUID; the existing decision survived its own challenge cycle.
- **Stack-canonical:** UUID is the Postgres-native PK for multi-tenant SaaS in 2026 (S2, S8). Better Auth's UUID option (F1) aligns.
- **Threat model:** UUID defeats enumeration; BIGSERIAL leaks (F4 + S7).
- **B-tree locality:** UUIDv7 ≈ BIGSERIAL on locality + ~50% better than UUIDv4 (F3 + S5). Postgres 17 needs a SQL helper for v7 today; native ships in Postgres 18.

UUIDv7 is the technically-stronger choice for B-tree locality; UUIDv4 is the simpler default available today on Postgres 17. Both defeat enumeration. **Recommendation:** UUIDv7 if BokChoy is willing to transcribe pgledger's MIT-licensed `pgledger_uuidv7_microsecond()` SQL function into the bootstrap migration; UUIDv4 otherwise. /design picks. The decision is reversible — UUIDv4 → UUIDv7 migration is a column-default change + a backfill (existing v4 IDs stay, new IDs become v7), no data-shape change.

`[[wallet-mechanics]]` §3/§5/§6 references to `player_id BIGINT` are stale per the original 2026-05-02 versioning; superseded by `[[player-auth]]` §2's UUID choice; reaffirmed by this research entry. The §6 anon_id collision math currently derived at 63-bit BIGINT projection becomes obsolete — UUID width has no plausible-scale collision concern (122 random bits → ~5×10⁻²⁰ at 1B players, meaningless).

## Conflicts

### Conflict 1 — `[[player-auth]]` UUID vs `[[wallet-mechanics]]` BIGINT

**Disagreement.** `[[player-auth]]` (2026-05-03) §2: `players.id UUID DEFAULT gen_random_uuid()`. `[[wallet-mechanics]]` (2026-05-02) §3, §5, §6: `player_id BIGINT NOT NULL` ~25 references including the §6 anon_id projection math.

**Per *Contradiction protocol*:** newer focused design pass beats older. `[[player-auth]]` is the authoritative source on player IDs; it surveyed the player-auth design space and committed UUID for stated reasons. `[[wallet-mechanics]]` was written before that pass and inherited an unverified BIGINT assumption.

**Resolution surface for /design:** amendment to `[[wallet-mechanics]]` §3, §5, §6 — column types swap `BIGINT` → `UUID` across `transactions.player_id`, `loot_rolls.player_id`, `iap_receipts.player_id`. §6 *Anon_id collision math* paragraph retires (no plausible-scale collision concern at 122-bit width). §6 HMAC projection rewrites from `('x' || encode(substring(...), 'hex'))::bit(63))::bigint` to a UUID-shaped projection — taking 16 bytes of HMAC-SHA-256 output, forcing v4 version + variant bits per RFC 9562 §5.4 to produce a valid UUID. *Revisit when* trigger about player count exceeding 10M is also retired.

### Conflict 2 — UUIDv4 vs UUIDv7 for BokChoy's Postgres 17

**Disagreement.** S5 benchmark + S6 spec evidence favor UUIDv7 on B-tree locality + index size. But Postgres 17 doesn't ship native `uuidv7()` — BokChoy needs either pgledger's SQL helper transcribed into the bootstrap migration, or accept UUIDv4 and migrate when Postgres 18 lands on Supabase.

**Per *Contradiction protocol*:** both are correct; the trade-off is "ship today with UUIDv4 + small future migration" vs "ship today with UUIDv7 + ~10 lines of vendored SQL."

**Resolution surface for /design:** small forking decision. Cost of UUIDv7 today is one migration with `pgledger_uuidv7_microsecond()` SQL function transcribed (MIT, ~10 lines). Benefit at BokChoy MVP scale (~3 writes/sec/project) is ~zero. Benefit at Studio+ scale (~575 writes/sec/project, 240M-row `transactions` projection) is the ~25% index-size delta from S5 + the insert-locality delta. /design picks; if the answer is "UUIDv4 today, migrate to v7 when Postgres 18 ships on Supabase," vault that as the chosen path with the explicit revisit-when trigger.

### Conflict 3 — Better Auth default 32-char alphanumeric vs UUID

**Disagreement.** Better Auth ships TEXT 32-char alphanumeric by default. BokChoy needs UUID for RLS GUC casting compatibility + canonical Postgres-stack convention.

**Per *Contradiction protocol*:** no contradiction; Better Auth supports UUID via documented `advanced.database.generateId: "uuid"` config. Resolution: BokChoy explicitly sets the option in Better Auth config. Vault as a cascade obligation: the auth-config workspace (`apps/auth-config` per workspace skeleton) must include this setting in the Better Auth instance configuration.

## Conditions

The findings above hold under:

- **Better Auth at commit `6b03a45a` (2026-05-03).** The `advanced.database.generateId` option is current as of this date. Future Better Auth changes could rename/restructure the option — track via Renovate.
- **Postgres 17 (BokChoy's current per `[[local-docker]]` `supabase/postgres:17.6.1.113`).** UUIDv7 native function ships in Postgres 18 only. Migration path: UUIDv4 today → UUIDv7 when Supabase ships Postgres 18 on managed tier (no firm date as of 2026-05-04 research).
- **Threat model includes external probing of customer-developer-exposed IDs.** F4's enumeration-attack rejection of BIGSERIAL assumes IDs are exposed through API surfaces. If BokChoy ever ships a fully-internal-only ID (unexposed to customers, dashboards, or third-party integrations), BIGSERIAL becomes available again on those columns specifically.
- **Better Auth org plugin table name `organization` (lowercase singular).** Verified via source-walk. If Better Auth versions before this commit used a different name, the FK target string in the `projects` schema baseline (F6) would need adjustment.

The findings break if:
- A new Postgres release ships `uuidv7()` natively (Postgres 18 confirmed; future versions may add v8/v9 with different properties). Forward-compatible — the migration path supports it.
- A future Better Auth release changes the runtime ID generator. The config option name might rename; track via Renovate + Better Auth release notes.

## Operational implications

For /design:

### Q1 (G1) — `players.id` resolution

**Resolved:** UUID. `[[player-auth]]` §2's UUID choice stands. `[[wallet-mechanics]]` §3/§5/§6 `player_id BIGINT` references amend to UUID (cascades the column type changes; retires the §6 BIGINT collision math; rewrites the §6 HMAC→UUID projection; retires the *Revisit when* 10M-player trigger).

**UUIDv4 vs UUIDv7 sub-decision:** /design picks. Recommendation lane: UUIDv4 today (`gen_random_uuid()` Postgres-native + `crypto.randomUUID()` TS), migrate to UUIDv7 when Supabase ships Postgres 18 on managed tier. Alternative: transcribe pgledger's `pgledger_uuidv7_microsecond()` SQL function into BokChoy's bootstrap migration today (~10 lines, MIT-licensed) — buys UUIDv7 immediately at Postgres 17, drops cleanly on Postgres 18. Both are valid; both are reversible.
