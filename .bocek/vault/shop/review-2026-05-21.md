## Findings

### [DRIFT] — BC010 wire code is `INSUFFICIENT_FUNDS`, but the wallet HTTP contract pins `BC010`

**Vault says:** `[[wallet/wallet-http-contract]]` G5 (error response shape): *"`{ "error": { "code": "BC010", "message": "Insufficient funds", "walletId": "...", "requested": 100, "available": 50 } }`. The `WalletError.code` becomes `body.error.code`."* — the wire `error.code` for insufficient funds is the raw BcCode `BC010`.
**Code does:** `apps/backend/src/infra/error-middleware.ts` now carries `BC_FRIENDLY_CODE = { BC010: 'INSUFFICIENT_FUNDS' }` and emits `BC_FRIENDLY_CODE[err.code] ?? err.code`, so `body.error.code` is `INSUFFICIENT_FUNDS` (422) from **both** the wallet `/debit` routes and shop `/purchases`. SDK `InsufficientFundsError` (`packages/sdk-node/src/errors.ts`) + `http.ts` dispatch + `http.test.ts` all assert the new code.
**Discrepancy:** the global error middleware changed a customer-facing wire code across two routes. `[[shop/shop-contract]]` (35)/(129) *asserted* `INSUFFICIENT_FUNDS` already existed ("Reuses BC010 `INSUFFICIENT_FUNDS`") — it did not; the shipped reality was the raw `BC010` per the wallet contract. The human authorized the change mid-implementation, but no vault entry records it and `[[wallet/wallet-http-contract]]` G5 still documents `BC010`.
**Severity:** major
**Severity rationale:** contract violation in a user-facing path (the error code customers dispatch on), which sits at the major/critical line. Held at major, not critical, because the code is the *intended* behavior (human-authorized, tested) — the defect is vault staleness + an unrecorded cross-route wire change, not a runtime bug or data-correctness issue.
**Recommendation:** `/design` — but mechanical, NOT research. Nothing to find: the decision is made and code + SDK + tests ship it. Pure vault catch-up — update `[[wallet/wallet-http-contract]]` G5 to show `INSUFFICIENT_FUNDS`, document the `BC_FRIENDLY_CODE` layer, and record the BC010→`INSUFFICIENT_FUNDS` + `InsufficientFundsError` decision (no entry captures it). The code is right; the vault is stale.
**Reproducibility:** reproducible — any reviewer reading G5 line 172 against `error-middleware.ts` reaches this.

### [GAP] — zero-`offer_items` offer charges the player and grants nothing

**Vault says:** `[[shop/shop-contract]]` (iii) "partial fulfillment is impossible" and Contract side-effects (130): "exactly one `currency_debit` + one `item_grant` per offer item."
**Code does NOT:** enforce ≥1 `offer_items` row. `purchase_offer_by_external_id` (migration 0013) resolves the price, debits, then loops over zero `offer_items` → 1 debit, 0 grants. The wrapper/route surface this as `granted: []` with a successful 201. The schema cannot express a ≥1-child constraint and no error code covers the case.
**Discrepancy:** an operator who creates a priced offer with no items produces a "charged, received nothing" purchase — the exact partial-fulfillment outcome the contract promises is impossible.
**Severity:** major
**Severity rationale:** a GAP against a contract guarantee ("partial fulfillment impossible") in a user-facing money path. Not critical because it requires operator misconfiguration (a zero-item offer) to reach, not a normal caller path; pre-catalog there is no UI to create one yet.
**Recommendation:** `/research` → `/design`. The drift is a sharp, falsifiable class question, not a blind design space: *does the game-economy SDK class permit a zero-content offer/bundle, and does it error at purchase or get prevented at catalog-create?* Re-query the `[[shop/.research/pricing-locus-research]]` sources; evidence picks between (a) operator invariant — offer-create enforces ≥1 item, no backend code/error — and (b) a new `BC093 EmptyOffer` raised by the SQL fn before the debit. This is the carried anti-improvisation flag from Slices 1–5, now formalized.
**Reproducibility:** reproducible — trace the SQL fn with an offer that has prices but no `offer_items`.

### [ORPHAN] — offer read responses expose an `active` field the contract doesn't list

**Code does:** `toOfferWire` (`apps/backend/src/shop/index.ts:281`) returns `active` on every offer in `GET /v1/offers` and `GET /v1/offers/{offerCode}`. The field flows through `OfferView` (`packages/shop/src/offer-view.ts`) and the SDK `ShopOffer` (`packages/sdk-node/src/shop.ts`).
**Vault gap:** `[[shop/shop-contract]]` Contract reads (132) enumerates the offer read shape as `{ code, displayName, description, prices, items }` — no `active`. The field is consistent across all three layers but unrecorded in the contract.
**Severity:** minor
**Severity rationale:** ORPHAN with no side effect (an extra read-only response field, no state change, no external call). On `GET /v1/offers` it is always `true` (the list is active-filtered) — redundant; on `GET /v1/offers/{offerCode}` it is genuinely informative (that read is *not* active-filtered, so a caller can see an inactive offer's state).
**Recommendation:** `/research` (fold into the GAP's pass) → `/design`. Narrow question: *does the class expose offer activation state on reads (boolean, à la Stripe Price `active`) or only via filtered lists?* Then `/design` adds `active` to the (132) read shape (it earns its place on `getOffer`) or drops it. Low stakes (one field) — do not spin a separate research session.
**Reproducibility:** reproducible — compare (132) field list against `toOfferWire`.

## Patterns observed

- **Cross-primitive monetary-wire-type inconsistency (not drift — each side matches its own contract).** Shop emits `paid.amount` and offer-price `amount` as JSON **numbers** (per `[[shop/shop-contract]]` (viii)/(132), which I followed). Wallet emits `balance`/`amount` as **strings** (per the wallet/balance-history contracts, NUMERIC-precision-preserving). A customer using both `bokchoy.wallet.balance()` and `bokchoy.shop.purchase()` sees `amount` typed differently across the two namespaces. Both are contract-compliant, so this is not a code-vs-vault drift — it is a cross-contract DX wart worth a `/design` reconciliation (pick one wire representation for money, or document the deliberate split). Surfacing because it will not show up as drift in any single-feature review.
- **Both self-introduced findings (DRIFT BC010, ORPHAN `active`) are places where the implementation seat made a defensible local choice and recorded the *rationale in code/state.md but never in the governing contract*.** The lesson for the next implementation pass: a wire-shape choice that deviates from or extends the contract is a vault write, not just a code comment — otherwise it surfaces as drift the moment anyone re-reads the contract.
